## 📋 Промт для создания документации по пакету (инструкция ассистенту)

```
Я работаю над ROS2-проектом SOARM101 (роботизированная рука). Мы используем двухуровневую документацию: мета-README (глобальный) и отдельный README для каждого пакета.

Твоя задача — проанализировать пакет по его дампу (структура + файлы) и сгенерировать README.md для этого пакета по нашему стандарту.

### СТАНДАРТНАЯ СТРУКТУРА README ДЛЯ ПАКЕТА:

```markdown
# <package_name>

<Краткое описание пакета (1–2 предложения)>

---

## Назначение

- Список ключевых функций (до 5 пунктов)

---

## Архитектура и ключевые особенности

- Описание классов, структур, основных компонентов.
- Если есть несколько классов (leader/follower), объяснить различия.
- Если пакет конфигурационный — объяснить, какие файлы за что отвечают.

---

## Параметры конфигурации (если есть)

Таблица: параметр | тип | описание | пример

---

## Использование

- Примеры кода (Python/C++), команды запуска.
- Как пакет подключается к другим пакетам (зависимости, интеграция).

---

## Зависимости

- Список зависимостей (ROS-пакеты, системные библиотеки)

---

## Лицензия

- Тип лицензии (MIT / Apache-2.0)
- Ссылка на файл LICENSE (если есть)

---

## Версия

<MAJOR.MINOR.PATCH> (с пояснением, если изменения были)

---

## Поддержка

[Issues](https://github.com/cyberbanana777/so-arm101-ros2-pkgs/issues)
```

### ПРОВЕРКИ, КОТОРЫЕ НУЖНО ВЫПОЛНИТЬ ПРИ АНАЛИЗЕ ДАМПА:

1. **Соответствие метадокументации**: если в дампе обнаруживается расхождение с тем, что мы указали в глобальном README (например, топик называется по-другому, или сервиса нет) — нужно указать на это и предложить точечно поправить мета-документацию.

2. **Ошибки в коде**: если видишь опечатки (например, `flaot64` вместо `float64`, неправильные пространства имён, целочисленное деление, неправильные макросы регистрации) — нужно описать диагностику и предложить исправление.

3. **Версионирование**:
   - Если добавлены новые поля в msg без удаления старых — `MINOR` (например, 1.1.0).
   - Если изменены типы или удалены поля — `MAJOR` (2.0.0).
   - Если только исправления ошибок — `PATCH` (1.0.1).

4. **Лицензии**: проверить, что в пакете есть `LICENSE`, а для заимствованных компонентов — `ORIGINS.md` или `NOTICE`.

5. **Особые случаи**:
   - Если пакет в активной разработке — указать это в README.
   - Для leader-компонентов: отметить, что `effort` и `moving_flag` всегда 0.
   - Для конфигурационных пакетов (например, `soarm101_ros2_control`) — описать макросы и их параметры.

### ВЫХОДНОЙ ФОРМАТ:

Предоставь:
- **Готовый README.md** (полный текст) в кодовом блоке.
- Если есть замечания по метадокументации или коду — укажи их отдельно после README.

### ПРИМЕР ТВОЕГО ОТВЕТА:

```markdown
# <package_name>

<содержание README>

---

## 🔍 Замечания

- В метадокументации указан топик `/soarm101_telemetry`, но в пакете он называется `/motor_states`. Предлагаю исправить мета-README.
- В файле `MotorState.msg` опечатка: `flaot64` → `float64`.
```

### КОНТЕКСТ ПРОЕКТА (кратко):

- ROS2 Humble.
- Два аппаратных плагина: Leader (только чтение) и Follower (управление).
- Кастомные сообщения: `MotorState` (9 полей) и `MotorStates`.
- Телеметрия публикуется через `soarm101_telemetry_controller` в топик `~/motor_states`.
- Ретрансляция команд: `arm_relay` (топик) и `gripper_relay` (action).
- Визуализация: RViz с двумя RobotModel (TF Prefix: leader/follower), маркеры.
- Лицензия: MIT (для своих пакетов), Apache-2.0 для заимствований.

---

**Сейчас я пришлю тебе дамп пакета. Начни с анализа, затем сформируй README и укажи замечания, если они есть.**
```

## 🧠 Как использовать этот промт

1. В новом диалоге с ассистентом вставь этот текст **целиком**.
2. Затем пришли файл с дампом пакета (например, `package_dump.md`).
3. Ассистент проанализирует дамп и выдаст README по стандарту, а также заметки по ошибкам и расхождениям.
