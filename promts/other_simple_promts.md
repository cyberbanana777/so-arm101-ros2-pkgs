## 🧠 Все полезные промт-бэкапы из нашего диалога

### 1️⃣ Промт для анализа кода и поиска ошибок

**Когда использовать:** ты присылаешь код (или дамп), я ищу логические ошибки, опечатки, несоответствия, предлагаю исправления.

```markdown
**Задача:** Проанализировать предоставленный код/дамп пакета и найти все ошибки.

**Что нужно сделать:**
- Проверить синтаксис, опечатки (например, `flaot64` → `float64`).
- Проверить логику: правильные ли пространства имён, верные вызовы методов, корректные типы данных.
- Проверить соответствие между заголовочными и исходными файлами (если есть).
- Проверить регистрацию плагинов (для ros2_control).
- Обратить внимание на потенциальные проблемы с производительностью (например, целочисленное деление).
- Указать на расхождения с документацией (если она есть).

**Формат ответа:**
- Для каждой ошибки: **диагностика** (что не так) → **решение** (как исправить).
- В конце — краткий чек-лист исправлений.

**Пример использования:** «Проанализируй этот код, найди все ошибки.»
```

---

### 2️⃣ Промт для рефакторинга и улучшений

**Когда использовать:** нужно переписать часть кода (например, заменить парсинг на yaml-cpp, разделить на два класса, добавить параметры).

```markdown
**Задача:** Переписать/рефакторить код в соответствии с новыми требованиями.

**Что нужно сделать:**
- Описать текущую проблему (например, ручной парсинг YAML ненадёжен).
- Предложить новую архитектуру (использовать библиотеку, разделить на классы, добавить параметры).
- Привести полный код новых/изменённых файлов.
- Указать, какие зависимости нужно добавить в CMakeLists.txt и package.xml.

**Формат ответа:**
- Пояснение, почему текущий код нужно изменить.
- Новый код с комментариями (где нужно).
- Инструкция по интеграции (например, «Добавь зависимость yaml-cpp в CMakeLists.txt»).
- Чек-лист для проверки после рефакторинга.

**Пример использования:** «Перепиши парсинг калибровки на yaml-cpp.»
```

### 3️⃣ Промт для написания новой ноды/скрипта

**Когда использовать:** нужно создать новый Python/C++ узел (например, ретранслятор, маркер-паблишер, статический TF-паблишер).

```markdown
**Задача:** Написать новый узел/скрипт для ROS2 (Python или C++).

**Требования:**
- Указать входные данные (подписка на топик, параметры).
- Указать выходные данные (публикация в топик, action-клиент/сервер).
- Логика работы (как обрабатывать данные).
- Обработка завершения (try-except, корректный shutdown).
- Параметры (declare_parameter с описанием).

**Формат ответа:**
- Полный код скрипта с комментариями.
- Инструкция по добавлению в launch-файл (если нужно).
- Инструкция по добавлению в CMakeLists.txt/setup.py (если нужно).

**Пример использования:** «Напиши ноду для ретрансляции телеметрии лидера на фолловер через топик.»
```

---

### 4️⃣ Промт для настройки launch-файлов

**Когда использовать:** нужно модифицировать существующий launch-файл или создать новый с условной логикой.

```markdown
**Задача:** Модифицировать launch-файл для добавления новой логики/параметров.

**Что нужно сделать:**
- Добавить новые аргументы (DeclareLaunchArgument).
- Изменить логику запуска (например, условный запуск контроллеров в зависимости от arm_type).
- Добавить обработчик завершения (OnShutdown + TimerAction).
- Убедиться, что все ноды имеют правильные namespace.

**Формат ответа:**
- Полный код launch-файла с комментариями.
- Пояснение, что изменилось и зачем.

**Пример использования:** «Добавь в bringup.launch.py условный запуск контроллеров только для follower.»
```

### 5️⃣ Промт для версионирования и лицензирования

**Когда использовать:** нужно определить, какую версию поставить пакету, или разобраться с лицензионными требованиями.

```markdown
**Задача:** Определить версию пакета и проверить лицензионную чистоту.

**Что нужно сделать:**
- На основе изменений определить, увеличивать MAJOR, MINOR или PATCH.
- Проверить, что в пакете есть файл LICENSE (и NOTICE/ORIGINS.md для заимствований).
- Объяснить требования лицензии (что нужно сохранить, какие уведомления добавить).

**Формат ответа:**
- Рекомендуемая версия (с обоснованием).
- Чек-лист лицензионной чистоты (что есть, чего не хватает).

**Пример использования:** «Я добавил два новых поля в MotorState.msg. Какую версию поставить?»
```

### 6️⃣ Промт для объяснения концепций (как для чайника)

**Когда использовать:** нужно просто и понятно объяснить какую-то сложную тему (QoS, пространства имён, кватернионы, open_loop_control).

```markdown
**Задача:** Объяснить [концепцию] максимально просто, как чайнику.

**Что нужно сделать:**
- Использовать аналогии из реальной жизни.
- Избегать сложных терминов (или сразу их расшифровывать).
- Привести практический пример из нашего проекта.
- Дать краткую шпаргалку (если применимо).

**Формат ответа:** объяснение + примеры + шпаргалка.

**Пример использования:** «Объясни, что такое open_loop_control в joint_trajectory_controller, простыми словами.»
```

---

### 7️⃣ Промт для генерации утилит (скриптов)

**Когда использовать:** нужно написать вспомогательный скрипт (генератор дампа, конвертер STL, анализатор логов).

```markdown
**Задача:** Написать утилиту/скрипт для [описание задачи].

**Требования:**
- Скрипт должен принимать аргументы (argparse).
- Должен обрабатывать ошибки (try-except).
- Должен выдавать понятные сообщения пользователю.
- Формат вывода — Markdown, текст или другой указанный формат.

**Формат ответа:**
- Полный код скрипта.
- Инструкция по запуску с примерами.

**Пример использования:** «Напиши скрипт для рекурсивного дампа всей папки src в один Markdown-файл.»
```

## 🎯 Как использовать эти промты

1. Сохрани этот список в отдельный файл (например, `prompts_backup.md`).
2. В будущем, когда перед тобой встанет задача (например, «нужно написать новую ноду»), скопируй соответствующий промт, вставь в диалог с ассистентом и добавь конкретные детали твоей задачи.
3. Ассистент поймёт формат и начнёт работать по знакомой схеме.
